### Why SQLAlchemy

SQLAlchemy is what turns a folder of trail-camera media into a queryable, analyzable dataset, without ever touching the original files:

- **A Sidecar Database, Not a Mutated Archive**: Opening a folder creates a `photos.db`/`videos.db` SQLite file *inside that same folder*, alongside - never overwriting - the original NPS-owned images and video. Every detection, tracked entity, calibrated speed, and computed direction lives in that sidecar database, so results can be regenerated, filtered, or thrown away without any risk to the source media.
- **Relationships That Mirror the Real Problem**: The `Image`/`Video` → `Instance` → `Entity` object relationships map directly onto the domain: one `Instance` is one detected box in one image, and an `Entity` groups the `Instance`s that are believed to be the same real visitor over time. SQLAlchemy's ORM, cascading foreign-key deletes, and a couple of hand-written SQLite triggers keep that graph consistent (e.g., automatically deleting an `Entity` once its last `Instance` is removed or reassigned).
- **Filtering in SQL, Not in Python**: The desktop app's filter UI (date ranges, entity type, direction, speed, cluster size, and more) compiles directly into SQLAlchemy `Select`/`join`/`where` queries executed by SQLite itself. That means filtering a season's worth of photos scales with the database engine instead of loading every row into memory and filtering in a Python loop.
- **Idempotent Schema Evolution Without a Migration Framework**: As the schema grew (new columns for calibrated speed, direction, analysis status), `after_create` events run guarded `ALTER TABLE ... ADD COLUMN` statements against older per-folder databases - a lightweight, dependency-free alternative to pulling in a full migration tool like Alembic for a project of this scope.

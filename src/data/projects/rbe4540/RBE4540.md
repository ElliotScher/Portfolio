## Summary

**Vision-Based Robotic Grasping** is an autonomous perception-to-grasp pipeline developed for WPI's RBE 4540 (Robot Manipulation) final project. A Kinova Gen3 lite 6-DOF arm with a wrist-mounted Intel RealSense D405 depth camera captures the tabletop from multiple viewpoints, fuses the views into a single point cloud, removes the table, separates the remaining points into individual objects, and computes a stable two-finger grasp that the arm then executes. The system was developed and validated in Gazebo simulation first, and then the same code was deployed on the physical robot by swapping only YAML configuration files.

***

## Context

Grasping an unknown object is one of the core problems in robot manipulation. Unlike a pick-and-place cell where every part arrives at a known pose, a general-purpose manipulator has to work out from raw sensor data where an object is, what shape it is, and where its fingers can make contact without the object slipping out. A single depth image only shows one side of an object, so the robot also has to reason about geometry it can't directly see.

To address this, the project implements the full pipeline from raw depth data to a lifted object:

* **Multi-View Perception**: The arm moves the wrist camera to several poses around the workspace and transforms each captured point cloud into the robot's base frame using TF2, giving a more complete view of each object than a single snapshot.
* **Geometric Grasp Synthesis**: Instead of a learned grasp model, grasps are derived analytically from surface normals and friction cones, so every chosen grasp can be explained and debugged.
* **Kinematically Aware Execution**: Candidate grasps are ranked and checked against the arm's reachability and collision constraints before any motion is commanded.

The system was designed around the following constraints:
* Must run identically in simulation and on hardware, with all tunable parameters kept in configuration files.
* Must segment and grasp multiple objects on a cluttered tabletop.
* Must only command grasps that the arm can reach along collision-free, straight-line approach and lift paths.
* Must tolerate imperfect alignment between real camera views, which leaves stray layers of table points behind.

## System Design

The code is split into two ROS 2 packages that communicate over topics:

* **`cvproc` (C++ / PCL)**: Point cloud merging, filtering, segmentation, clustering, and grasp synthesis.
* **`kinova_sim` (Python / MoveIt)**: Simulation and real-robot launch files, moving the camera between viewpoints, and executing the selected grasp.

### Point Cloud Preprocessing

1. **Merge**: Each view is transformed into `base_link` with TF2, concatenated, and voxel-downsampled to remove duplicate points where the views overlap (about 305k raw points reduced to about 23k in simulation).
2. **Workspace Filter**: A PCL `CropBox` cuts away the floor, table legs, and background, leaving only the table top and what sits on it.
3. **Table Segmentation**: RANSAC fits a plane to the table. The plane is removed, and its normal is reused later as the "up" direction and the reference for object height.
4. **Clustering**: Euclidean cluster extraction over a KD-tree splits the remaining points into separate objects and throws out small clusters as noise.

### Grasp Synthesis

* **Footprint Centroid**: The camera only sees the top and some sides of each object, so a plain average of the points is biased upward and toward the camera. The object center is instead taken as the center of its footprint on the table, halfway up its height.
* **Surface Normals**: Normals are estimated at every point and flipped to point into the object.
* **Contact Pair Search**: Every pair of points on an object is tested as a possible finger placement. A pair is kept only if both contact normals lie inside the friction cone along the line between them, the width fits inside the gripper, and the line is level enough for the open fingers to straddle the object on the way down. In simulation this cut roughly 640k candidate pairs on the cube down to about 14k feasible ones.
* **Scoring**: Feasible pairs are scored by how well the normals align and how close the grasp line passes to the object center. The lowest-cost pair wins, and the rest are kept as ranked backups.
* **Approach Vector**: PCA gives the object's major axis, and the gripper approaches perpendicular to both that axis and the closing direction. A few tilted variants of each grasp are also generated with a small cost penalty, so the ideal approach is preferred but the arm still has options when it can't reach it.

### Grasp Execution

The Python executor walks down the ranked list of grasps and keeps only the ones the arm can actually perform: it needs a collision-free IK solution at a pre-grasp pose 10 cm back along the approach direction, a feasible straight-line Cartesian path in to the grasp, and a feasible straight-line lift. The best remaining grasp is then executed: open the gripper, move to the pre-grasp pose, move straight in, close, and lift.

### Moving to Hardware

On the real robot the same nodes run under a launch file that also starts the Kortex arm driver and RealSense camera. Only configuration changes: the arm captures four views instead of two, the workspace box and table height match the lab table, and the object height threshold is stricter to reject the extra layers of table points left behind by small misalignments between real camera views.
